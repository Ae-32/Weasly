# AI Workflow Rules — Weasly

## Approach

Build this project incrementally using a spec-driven workflow.
Before writing any code for a feature, read `project-overview.md`,
`architecture.md`, `code-standards.md`, and `ui-context.md` in
`context/`, plus the relevant spec file in `context/specs/`. Always
implement against what these files say — never guess or invent
behavior that isn't defined in them. If something needed isn't
defined anywhere, stop and ask instead of assuming.

The person building this project is not a professional developer
and only knows the basics. Every time you implement something,
explain in plain, non-technical language: what the piece of code
does, how it works, what tools/packages it needs, and why it's
needed — before or alongside the technical explanation. Do not
assume familiarity with programming jargon.

## Scoping Rules

- Work on one feature unit at a time (e.g. "Transactions", not
  "Transactions and Budgets together")
- Prefer small, verifiable increments over large speculative
  changes
- Do not combine unrelated system boundaries in a single
  implementation step (e.g. don't touch `services/` and
  `screens/` for two different features in one step)
- Do not add packages, screens, or features that aren't part of
  the current unit's spec, even if they seem like a natural
  next step

## When to Split Work

Split an implementation step if it combines:

- UI changes (a screen/widget) and data-layer changes (Firestore
  service code) for two different features
- Multiple unrelated screens or providers
- Behavior not clearly defined in the context files or the
  current spec

If a change can't be tested end-to-end in the app quickly, the
scope is too broad — split it into smaller steps.

## Handling Missing Requirements

- Do not invent product behavior not defined in
  `project-overview.md`, `architecture.md`, or the current spec
  file
- If a requirement is ambiguous (e.g. "what happens if a user
  deletes a category that has transactions in it?"), stop and
  ask instead of guessing
- If a requirement is genuinely missing, add it as an open
  question in `progress-tracker.md` before continuing, so it
  doesn't get forgotten

## Protected Files

Do not modify the following unless explicitly instructed:

- Any file inside `context/` — these are planning documents, not
  code, and should only change when a decision actually changes
- Firebase configuration files (`firebase_options.dart`,
  `google-services.json`) — these are generated by the Firebase
  setup tools, not hand-written
- Any third-party package's internal files (never edit code
  inside the `pub` package cache)

## Keeping Docs in Sync

Update the relevant context file whenever implementation changes:

- `architecture.md` — if the tech stack, folder structure, or an
  invariant changes
- `code-standards.md` — if a new coding convention is introduced
- `project-overview.md` — if a feature's scope changes
- `progress-tracker.md` — after every meaningful step, always

## Before Moving to the Next Unit

Before marking a unit complete in `progress-tracker.md`, confirm:

1. The feature works end to end, tested by actually running the
   app — not just "the code looks right"
2. No invariant defined in `architecture.md` was broken
3. The verification checklist in that unit's spec file is fully
   checked off
4. `progress-tracker.md` is updated to reflect what was completed
5. The app still runs with no errors (`flutter run` or `flutter
   analyze` passes cleanly)
